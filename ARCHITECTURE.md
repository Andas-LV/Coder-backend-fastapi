# Архитектура Coder Backend

Бэкенд чата с ИИ на FastAPI. Умеет: хранить чаты и сообщения, отвечать через LLM (Ollama Cloud) с потоковой выдачей, считать токены, задержку и стоимость, и **отвечать по PDF-файлам, приложенным к сообщению (RAG)** со ссылками на источники.

Стек: Python 3.12, FastAPI, SQLAlchemy 2 (async) + asyncpg, PostgreSQL + pgvector, Alembic, sentence-transformers (`BAAI/bge-m3` на GPU), Ollama, tiktoken, PyMuPDF, pytest, ruff, uv.

---

## 1. Общая картина

```
 Фронт (Next.js)
     │  HTTP + заголовок Authorization: Bearer <JWT NextAuth>
     ▼
┌─────────────────────────── app/ ───────────────────────────┐
│  api/        принимает запрос, проверяет вход, отдаёт ответ │
│     │                                                       │
│  services/   бизнес-логика: «что делать и в каком порядке»  │
│     │            ├── llm/         вызов языковой модели     │
│     │            └── embeddings/  превращение текста в вектор│
│  repositories/  все SQL-запросы к базе                      │
│     │                                                       │
│  models/     описание таблиц (SQLAlchemy)                   │
│  schemas/    формы JSON для запросов и ответов (Pydantic)   │
│  core/, db/  настройки и подключение к базе                 │
└─────────────────────────────────────────────────────────────┘
     │                                  │
     ▼                                  ▼
 PostgreSQL + pgvector            Ollama Cloud (LLM)
```

**Главное правило слоёв** (сверху вниз, не наоборот):

| Слой | Может вызывать | Не должен |
|---|---|---|
| `api/routes` | services, repositories (для простых чтений), schemas | содержать бизнес-логику и SQL |
| `services` | repositories, llm, embeddings | знать про HTTP (`Request`, коды ответов) |
| `repositories` | models, SQLAlchemy | знать про LLM и бизнес-правила |
| `models` | только `db/base.py` | знать про всё остальное |

Зачем это нужно: каждый слой можно проверить отдельно. Например, `ChatService` в тестах работает с поддельной моделью и поддельной базой (`tests/test_chat_service.py`), потому что он не привязан ни к HTTP, ни к конкретному SQL.

## 2. Папки и файлы

### `app/main.py`: точка входа
Создаёт приложение FastAPI, включает CORS (разрешены `CLIENT_URL` и `LOCAL_CLIENT_URL` из `.env`), подключает роуты. В `lifespan` при старте помечает как `failed` документы, которые остались в статусе `processing` после перезапуска сервера (фоновая индексация умирает вместе с процессом).

### `app/core/`: настройки
- `config.py`: класс `Settings` (pydantic-settings). Читает `.env` и даёт типизированные настройки: база, ключ Ollama, модель по умолчанию, параметры эмбеддингов и нарезки (`embed_model`, `embed_device`, `chunk_size`, `chunk_overlap`). Везде в коде: `from app.core.config import settings`.

### `app/db/`: подключение к базе
- `base.py`: `Base`, родитель всех моделей.
- `session.py`: async-движок, фабрика сессий `SessionLocal` и зависимость `get_session` (одна сессия на запрос).

### `app/models/`: таблицы (SQLAlchemy)
| Файл | Таблица | Что хранит |
|---|---|---|
| `user.py` | `users` | email, имя, аватар (создаётся при первом запросе по JWT) |
| `chat.py` | `chats` | заголовок, system prompt, модель чата, время |
| `message.py` | `messages` | роль, текст, модель, токены, задержка, стоимость, `sources` (источники ответа), `attachments` (файлы пользователя) |
| `document.py` | `documents` | приложенный PDF: имя, страницы, статус (`processing` / `ready` / `failed`), прогресс. Принадлежит чату |
| `chunk.py` | `chunks` | кусок текста PDF + его вектор (`Vector(1024)`) + индекс HNSW для быстрого поиска |

Связи: `User → Chat → Message`, `Chat → Document → Chunk`. Удаление родителя удаляет детей (`ON DELETE CASCADE`).

### `app/schemas/`: формы JSON (Pydantic)
- `chat.py`: что принимает и отдаёт API: `ChatCreate`, `ChatOut`, `ChatDetail`, `MessageOut`, `SourceOut`, `AttachmentOut`. Это «договор» с фронтом; они отделены от моделей БД, чтобы наружу не утекало лишнее.

### `app/api/`: HTTP-слой
- `router.py`: собирает все роуты в один `api_router`.
- `deps.py`: зависимости FastAPI:
  - `SessionDep`: сессия БД;
  - `CurrentUser`: проверяет JWT от NextAuth (подпись HS256 с `NEXTAUTH_SECRET`), достаёт email и находит или создаёт пользователя;
  - `MessagePayloadDep`: разбирает сообщение, пришедшее либо JSON, либо `multipart` (текст + PDF).
- `uploads.py`: проверка загружаемого PDF (тип, не больше 20 МБ).
- `routes/health.py`: `GET /health`.
- `routes/models.py`: `GET /models`: список бесплатных моделей, чтобы фронту не хранить его у себя.
- `routes/chats.py`: `POST/GET /chats`, `GET /chats/{id}`, `POST /chats/{id}/messages` (обычный ответ) и `POST /chats/{id}/messages/stream` (потоковый ответ по SSE). Здесь же превращение ошибок в HTTP-коды (404, 415, 413, 422, 502).

### `app/repositories/`: работа с базой (весь SQL здесь)
- `chat.py`: пользователи, чаты, сообщения, история диалога, `get_chat_document_ids` (какие файлы чата готовы для поиска).
- `document.py`: создание документа, пакетная запись кусков, статусы и прогресс, **векторный поиск** `search_chunks` (сортировка по `embedding.cosine_distance`, `score = 1 - distance`, фильтр по пользователю и статусу `ready`).

### `app/services/`: бизнес-логика
- `chat_service.py`: **главный файл проекта**. Оркестрирует сообщение: сохраняет вопрос, собирает историю, при наличии файлов ищет источники и строит prompt, вызывает модель, считает токены, задержку и стоимость, сохраняет ответ с `sources`. Для файлов: принимает PDF (`attach_files`), ждёт индексацию и шлёт прогресс (`_indexing_progress`).
- `document_service.py`: превращает PDF в данные для поиска: достаёт текст постранично (PyMuPDF), режет на куски, создаёт документ и **в фоне** считает эмбеддинги пачками по 16 (прогресс виден по ходу). Один документ индексируется за раз (`asyncio.Lock`).
- `chunking.py`: чистая функция `split_text` без зависимости от БД: режет текст рекурсивно (абзацы → строки → предложения → токены) на куски не больше `chunk_size` токенов с перекрытием.
- `model_catalog.py`: определяет, какие модели Ollama доступны бесплатно: пробный запрос на 1 токен к каждой, результат кэшируется на час.

#### `app/services/llm/`: языковые модели
- `base.py`: интерфейс `LLMProvider` (`generate`, `stream`, `list_models`, `check_model`) и общие структуры (`LLMMessage`, `LLMResult`, `LLMUsage`, `LLMChunk`).
- `ollama.py`: реализация для Ollama Cloud.
- `pricing.py`: цены за токены и расчёт стоимости (для Ollama Cloud цены нет, поэтому `cost_usd` пустой).
- `__init__.py`: `get_llm_provider()`: единственное место, где выбирается провайдер. Чтобы добавить, например, OpenAI, нужно написать новый класс по интерфейсу и поменять эту функцию. `ChatService` менять не придётся.

#### `app/services/embeddings/`: векторы
- `base.py`: интерфейс `EmbeddingProvider` (`embed_documents`, `embed_query`).
- `hf_local.py`: локальная модель `bge-m3` через sentence-transformers: грузится один раз, на GPU в `float16`, вызов через `asyncio.to_thread`, чтобы не блокировать сервер.
- `__init__.py`: `get_embedding_provider()`: синглтон.

### Вне `app/`
- `migrations/`: история изменений схемы БД (Alembic). Применение: `uv run alembic upgrade head`.
- `tests/`: `test_chunking.py` (нарезка), `test_chat_service.py` (RAG-логика с поддельной моделью), `test_message_payload.py` (разбор JSON и multipart).
- `pyproject.toml` / `uv.lock`: зависимости (uv), настройки ruff и pytest; `torch` берётся из CUDA-индекса PyTorch на Windows.

## 3. Что происходит при отправке сообщения

### Обычное сообщение
```
POST /chats/{id}/messages/stream  {"content": "..."}
  1. deps: JWT → пользователь; тело → MessagePayload
  2. routes/chats.py: найти чат (404, если чужой) → ChatService.stream()
  3. ChatService:
       сохранить вопрос → загрузить историю → вызвать модель (stream)
       → отдавать куски события `delta` → сохранить ответ (токены, latency, стоимость)
       → событие `done`
```

### Сообщение с PDF (RAG)
```
POST /chats/{id}/messages/stream  multipart: content + files
  1. deps: проверить PDF (415/413), максимум 5 файлов (400)
  2. attach_files: достать текст, нарезать, создать Document (processing)
       └ битый PDF или скан без текста → 422 сразу, ничего не сохраняется
  3. фон: эмбеддинги пачками по 16 → запись Chunk → status = ready
     пока идёт: событие `indexing` {chunks_done, chunks_total} каждые ~2 с
  4. сохранить вопрос с attachments
  5. ПОИСК: embed_query(вопрос) → search_chunks(top 5, только файлы этого чата)
  6. PROMPT: system prompt + инструкция «отвечай по источникам, ставь [1], [2]»
            + блок <sources>[1] файл, стр. N ... </sources>
  7. событие `sources` → `delta`... → `done` (в ответе сохранены `sources`)
```
Порядок событий SSE: `indexing` → `sources` → `delta` → `done` (или `error`).

## 4. Решения и причины

| Решение | Зачем |
|---|---|
| Интерфейсы `LLMProvider` и `EmbeddingProvider` | можно заменить провайдера, не трогая логику чата; в тестах подставляется подделка |
| SSE (потоковая выдача) | пользователь видит ответ по мере генерации, а не ждёт целиком |
| Индексация в фоне + прогресс | эмбеддинги тяжёлые; запрос не должен висеть без обратной связи |
| `asyncio.to_thread` для эмбеддингов | вычисления блокируют поток; иначе сервер перестал бы отвечать остальным |
| GPU + `float16` | на RTX 4050 около 35 мс на кусок против около 3 с на CPU; вдвое меньше видеопамяти |
| Блокировка на один документ за раз | CPU и GPU не делят между параллельными задачами |
| Токены, задержка, стоимость у каждого ответа | без метрик нельзя оценить качество и цену |
| Источники в JSONB у сообщения | цитаты не меняются, даже если файл потом удалят |
| Поиск фильтруется по пользователю | вектор одного пользователя не должен попасть в prompt другого |
| Текст источников помечен как данные | защита от prompt injection из содержимого PDF |
| Миграции Alembic | изменения схемы воспроизводимы и откатываются |

## 5. Как запустить

```bash
uv sync                                   # зависимости (на Windows ставит CUDA-сборку torch)
uv run alembic upgrade head               # схема БД
uv run uvicorn app.main:app --reload      # сервер
.venv\Scripts\python -m pytest            # тесты
.venv\Scripts\ruff check .                # линтер
```

> Пока сервер запущен, не запускайте `uv run ...`: `uv` попытается синхронизировать окружение и не сможет заменить занятые файлы `torch`. Используйте `.venv\Scripts\python -m pytest` или `uv run --no-sync`.

Нужен файл `.env`: `DATABASE_URL`, `NEXTAUTH_SECRET`, `CLIENT_URL`, `OLLAMA_API_KEY` (остальное имеет значения по умолчанию, см. `core/config.py`).

## 6. Если вы хотите стать ИИ-разработчиком: на что смотреть

В этом проекте уже есть почти весь «скелет» современного LLM-приложения. Вот что стоит изучить и где это лежит в коде.

### Ключевые понятия и где их увидеть

| Тема | Что понять | Где в проекте |
|---|---|---|
| **Токены и контекстное окно** | модель видит не слова, а токены; контекст ограничен, токены стоят денег | `chunking.py` (счёт через `tiktoken`), `pricing.py` |
| **Эмбеддинги** | текст превращается в вектор; близкие по смыслу тексты дают близкие векторы | `embeddings/hf_local.py` |
| **Векторный поиск** | как искать ближайшие векторы; косинусная близость; индекс HNSW | `models/chunk.py`, `repositories/document.py::search_chunks` |
| **Нарезка (chunking)** | размер куска и перекрытие решают качество поиска: слишком мелко теряется контекст, слишком крупно шум | `chunking.py` |
| **RAG** | найти нужные куски и подставить в prompt, чтобы модель отвечала по фактам, а не по памяти | `chat_service.py::build_rag_prompt` |
| **Prompt engineering** | чёткие инструкции, формат цитирования, поведение «если ответа нет, скажи» | `RAG_INSTRUCTIONS` в `chat_service.py` |
| **Prompt injection** | текст из документов может содержать «команды» для модели; их нужно считать данными | блок `<sources>` и вырезание `</sources>` |
| **Потоковая выдача** | SSE, асинхронные генераторы | `chat_service.py::stream`, `routes/chats.py` |
| **Async Python** | `async/await`, блокирующие вызовы выносят в потоки, фоновые задачи | `document_service.py` (`to_thread`, `create_task`) |
| **Наблюдаемость затрат** | токены, задержка, стоимость каждого ответа | поля `messages.*` |
| **Архитектура приложения** | слои, зависимости, подмена провайдеров | весь `app/` |
| **Миграции БД** | схема версионируется как код | `migrations/` |

### Известные слабые места (отличные задачи для практики)

1. **История диалога отправляется целиком.** На длинных чатах упрётесь в контекст и в цену. Задача: ограничить историю по токенам, суммировать старое.
2. **Поиск только векторный.** Для точных терминов (коды, имена) лучше **гибридный поиск** (вектор + полнотекстовый `tsvector`) и **reranking**.
3. **Нет порога релевантности.** Всегда берутся 5 кусков, даже если они бесполезны. Задача: отсекать по `score`.
4. **Нет оценки качества RAG (evals).** Сейчас нельзя измерить, стало ли лучше. Задача: набор вопросов с эталонными ответами и метрики (попадание нужного куска в top-5, верность ответа).
5. **Запрос для поиска это сырой текст последнего сообщения.** Для уточняющих вопросов («а что насчёт второго?») нужен **переписанный запрос** с учётом истории.
6. **Нарезка по токенам `cl100k` (tiktoken), а модель эмбеддингов `bge-m3` считает по-другому.** Размеры не совпадают точно; безопасно, но не идеально.
7. **Сканы PDF не поддерживаются** (нет текстового слоя). Задача: OCR.
8. **Нет лимитов запросов, удаления чата, тестов на реальной базе, логирования в одном формате.**
9. **Нет «агентов» и вызова инструментов (tool calling).** Следующая ступень: дать модели функции (поиск, калькулятор, база) и цикл «подумала → вызвала → ответила».

### Практический план изучения (в таком порядке)

1. **Прочитайте `chat_service.py` целиком** и объясните себе каждый шаг. Это ядро.
2. **Поиграйте с параметрами:** `CHUNK_SIZE`, `CHUNK_OVERLAP`, `top_k` (`RAG_TOP_K`), тексты инструкции, и смотрите, как меняются ответы. Так формируется интуиция.
3. **Сделайте evals** (пункт 4 выше): без измерений вы будете гадать.
4. **Добавьте гибридный поиск и порог релевантности.**
5. **Добавьте второй провайдер LLM** (по интерфейсу из `llm/base.py`): поймёте, зачем нужны абстракции.
6. **Изучите tool calling и агентов**, потом структурированный вывод (JSON по схеме).
7. **Деплой:** Docker, переменные окружения, GPU/CPU-эмбеддинги в облаке, мониторинг затрат.

### Совет
ИИ-разработчик в продуктовой команде чаще всего занимается **не обучением моделей, а инженерией вокруг них**: данные, поиск, prompt, оценка качества, стоимость, надёжность. Этот проект как раз про это. Лучшая практика: берите слабое место из списка выше, формулируйте, как измерить улучшение, и делайте его.
